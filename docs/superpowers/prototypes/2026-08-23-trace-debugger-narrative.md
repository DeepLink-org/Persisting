# Trace 调试器叙事（v2）

日期：2026-08-23
状态：叙事定稿候选，配套原型 `pchronicle-trace-debugger.html`

## 为什么要重写叙事

上一版叙事（"调试器 = 轨迹详情的 Debug 模式，像 IDE 一样"）有两个问题：

1. **它是 IA 答案，不是产品叙事。** 它回答"放在哪、怎么不冲突"，没有回答"这是什么、凭什么存在"。
2. **IDE 类比把新品类讲回了旧品类。** "像 IDE 的调试器"是从已有动词里组合出来的，这正是要避免的。

## 核心命题

> **Agent 的失败不是异常，是选择。**

传统软件的失败有清晰形态：抛异常、崩进程、超时。调试动作是"找到那行代码"。二十年工具链建立在这个前提上——stack trace 把你直接带到出错的行。

Agent 的失败没有这个形态。它不抛异常——它返回一个看起来完成了的结果；它不崩——它循环、犹豫、自信地说错话。失败被埋在一个"成功"的响应里。你拿到的不是 stack trace，是一个结果加一个问号。

所以 Agent 的调试动作不是"找那行代码"，而是**重建那个决定**。模型在 step 17 做出错误决定，是因为它当时看到的上下文缺了什么、多了什么、或误解了什么。

> **上下文窗口就是 Agent 的变量作用域。** 看不到 step N 时刻的上下文，一切归因都是猜。

## 三段叙事

### 第一段：从"看录像"到"回到现场"

Observability 给的是录像回放——站在场外看完整场比赛，看比分、看统计。但看录像永远无法知道球员在那一秒看到了什么。

pChronicle 录的不只是事件流，是每一步的完整世界状态（L0，warehouse，已建成）。所以"回到那一刻"是字面操作，不是比喻：scrubber 拖到 step 17，你看到的就是模型当时看到的，一个 token 不差。

### 第二段：调试对象从"系统"变成"决定"

分布式追踪 debug 的是系统（span、延迟、错误传播）；Agent 调试器 debug 的是决定。每一步都是决策点：在这个上下文下，模型选择了这个动作。

- **Step diff** 回答"这一步和上一步之间什么变了"——触发错误决定的变化往往就在这里。
- **断点**不设在代码行上，设在条件上（`tool 连续失败 ≥ 3`、`tokens > 10k`、`同一命令重复执行`）——因为 Agent 的"错误行"是模式，不是位置。

### 第三段：从"归因"到"重演"

看懂现场只是定性。要证明因果，唯一办法是重演：fork 到 step 17，只改一个变量（补上缺失的上下文 / 换 system prompt / 加约束），重跑，对照组就是原轨迹。

这是 L2，也是与所有 observability 工具的分水岭：**它们只能解释过去，pChronicle 能验证假设。**

## 形态语言（叙事如何决定 UI）

| 叙事 | UI 落点 |
|---|---|
| 时间旅行是标志性动作 | timeline 不是导航条，是时间轴本体；scrubber 一等公民，支持键盘 ←→ 与播放 |
| 界面以模型视角为第一视角 | 详情第一句话不是 "Trace details"，是 **"模型在 step N 这一刻看到了这些"**；不罗列 span 属性 |
| 每个异常都是入口 | 错误 / 信号 badge 点击即 "回到现场"——跳到该步点，上下文已重建。monitoring 语言到 investigation 语言的切换就发生在这一下点击 |
| 现场重于走廊 | trace 列表是门厅（找 case），调试器是现场（做归因）。IA 上仍收敛在 Traces 页内（见 v1 的模式结论），但叙事权重相反：查看器是通往现场的门厅，不是产品本体 |

## 一句话定位

> pChronicle 不是又一个加了调试功能的 traces 查看器，是第一个把"回到模型做决定的那一刻"做成字面操作的调试器。
