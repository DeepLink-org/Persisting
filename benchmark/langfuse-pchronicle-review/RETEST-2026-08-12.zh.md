# pChronicle 优化后复测（2026-08-12）

## 结论

**[INFERRED, HIGH] 本次 lazy catalog / source-pruning 优化有效；按“serverless Lite tracing backend”范围，性能与可靠性可以进入 Conditional GO 原型阶段。**

[COMPUTED, HIGH] 相同 113,000-row fixture 下，catalog cold start 从 2,104.04 ms 降到 35.04 ms，warm point/list/simple aggregate P95 分别改善 34.8%/49.9%/63.2%。

[COMPUTED, HIGH] 当 adapter 能把 Run 映射成 exact `_file_` predicate 时，catalog point P95 为 3.01 ms；此前记录的 ClickHouse point P95 为 4.83 ms。这个本地结果说明 per-Run Lance format 不是 point path 的主要性能障碍。

[COMPUTED, HIGH] project-path pruning 后 list P95 为 167.17 ms，满足 Lite 场景 1 s 绝对门槛，但仍是 ClickHouse 记录值的 56.3×。跨 Run list/aggregate 仍是主要差距。

[KNOWN, HIGH] full Langfuse v4 harness 仍会报告 unsupported mutation/delete/FTS/dashboard/Parquet 和 duplicate-version 语义。这些能力本次没有实现；若 Lite profile 明确关闭它们，就不应把它们解读成性能回归。

## Lazy/pruning 路径

| Path | Catalog/open | Query P95 | End-to-end approximation |
|---|---:|---:|---:|
| fresh global point，210 sources | 10.84 ms | 302.94 ms | `[COMPUTED, HIGH]` 313.77 ms |
| fresh global list，210 sources | 12.47 ms | 326.68 ms | `[COMPUTED, HIGH]` 339.16 ms |
| direct Run point | 0.51 ms | 2.14 ms | `[COMPUTED, HIGH]` 2.64 ms |
| exact `_file_` catalog point | 12.34 ms | 3.01 ms | `[COMPUTED, HIGH]` 15.35 ms |
| project `_file_ LIKE` list | 12.02 ms | 167.17 ms | `[COMPUTED, HIGH]` 179.20 ms |

[INFERRED, HIGH] 结果支持此前的因果判断：主要瓶颈是跨 Run fan-out，而不是 Lance 文件格式。exact source 被选中后，catalog provider 能在 resolve 前排除其他 209 个 source，point latency 即降到毫秒级。

[INFERRED, HIGH] Langfuse Lite adapter 必须把已知 project/trace/Run 映射成 `_file_` predicate 或直接 Run URI；只传 `agent_id/event_id` 会触发全 catalog source resolution，丢失本次优化的大部分收益。

[COMPUTED, HIGH] restart 的 append+catalog 为 51.76 ms，随后首次全局 visibility query 为 344.02 ms，端到端 395.78 ms且目标行可见。该拆分避免把 lazy catalog 的快速构建误报成完整 restart latency。

## Rules checked

- [KNOWN, HIGH] Per `schema-pk-prioritize-filters` / `schema-pk-filter-on-orderby`：exact `_file_` 相当于先使用物理 source key；这是新版 point path 的关键合规点。
- [KNOWN, HIGH] Per `schema-partition-low-cardinality`：per-Run source 仍是高基数布局；lazy resolution 缓解 metadata/open cost，但 project-wide query 仍随选中 Run 数增长。
- [KNOWN, HIGH] Per `query-index-skipping-indices`：source-level pruning 已有效；source 内 `event_id/time` scalar index 仍可进一步降低 scan。
- [KNOWN, HIGH] Per `schema-types-native-types` / `schema-json-when-to-use`：当前 timestamp/known Langfuse fields 仍偏 UTF-8/opaque JSON；这更影响跨 Run sort/aggregate，而非已路由的 point。
- [KNOWN, HIGH] Per `query-mv-incremental`：Lite profile 若不做 dashboards，可暂不引入完整 OLAP MV；若未来需要 project-wide analytics，应增加小型 typed projection，而不是重新 eager-normalize catalog。
- [KNOWN, HIGH] Per `insert-batch-size` / `insert-async-small-batches`：本次优化未改善 append throughput；per-Run commit/fragment batching 仍是独立优化方向。

## 判定

[INFERRED, HIGH] 对明确缩减能力的 `PCHRONICLE_LITE`：性能、cold start、内存、visibility 和 durability 达到本次 dev-scale absolute gates，可以继续实现 adapter prototype。

[INFERRED, HIGH] 对完整 ClickHouse-compatible backend：项目级查询相对 ClickHouse 的差距和未实现语义仍存在，因此旧的 full-v4 NO-GO 不被本次性能优化推翻。

[INFERRED, HIGH] 下一优先级不是替换存储格式，而是让 adapter 强制走 project/Run source pruning，并增加 project-level run index；之后再测 1/10/100/1000 Runs 的规模曲线。
